The product

What it does, and why the language part is the easy half

Route Gen AI turns a plain-English ride request into ranked, Garmin-importable GPX routes on a map, and then lets you edit them by talking to them — “avoid Whitney Way”, “make it ten miles longer”, “add a stop at Olbrich”. It exists because route planners make you draw, and drawing a 40-mile loop that avoids one particular road is tedious in a way a sentence is not.

The technically interesting part is not the parsing. A language model reads “under 2000 feet of climbing” correctly on the first try. The hard part is that a route is a geometric object with physical constraints, and language models cannot be trusted to produce one. So the architecture puts the model in exactly one place, at the front, translating intent — and everything after it is ordinary deterministic code that generates candidates and throws away the ones that do not measure up.

That split is also what makes this evaluable. Because the acceptance criteria are computed, the eval can use the same kind of computation to check them — independently, from the file on disk.

How it works

One model call, then arithmetic

1. ParseThe only model call. claude-haiku-4-5 with a JSON schema turns the sentence into a typed spec: distance, shape, climb cap, waypoints, avoid list. Enum-locked, no tools, no agent loop.
→
2. ClampEvery number the model emitted is bounded server-side. A schema-valid request can still say “300 miles”; the clamp pulls it to 150 and logs that it did.
→
3. GenerateSelf-hosted BRouter over OSM. Loops are synthesized by placing via-points on a circle through the start, swept across compass bearings and rescaled toward the target length.
→
4. Rank & rejectComputed, never judged: distance tolerance, climb ceiling, fraction of road ridden twice, meters on major highways. Rejections carry reasons.
→
5. GPXWritten as a GPX 1.1 track with elevation, importable to Garmin Connect as a course.

The outlined box is the only step a language model touches. Steps 2–5 are deterministic, run offline in tests, and are where every claim in this report is verified.

Why it is built this way: a hostile or confused request can only produce weird-but-schema-valid values, which the clamp bounds — it can never produce geometry. The blast radius of a bad parse is one wrong number, not a route through a lake.

Method

What counts as a pass, decided before the run

62 requests were written as a versioned set (routegen-eval-v1) with expectations frozen on 2026-09-19. They are split five ways on purpose: straightforward asks, hard combinations, ambiguous asks, requests the system should decline, and requests naming features the product does not have.

Each case is graded on three separate questions, because conflating them hides where a failure actually is:

  • Did it understand? The parsed spec is compared field-by-field against the frozen expectation — distance in range, correct shape, correct edit mode, waypoints present.
  • Did it produce something valid? The GPX is re-parsed with a real XML parser (the app itself uses regexes) and checked for range-valid coordinates, finite elevations, continuity, and at least two points.
  • Does it satisfy the sentence? Distance measured by haversine over the geometry, loop closure, start proximity, closest approach to each requested waypoint, meters still ridden on a road the user excluded, climb against a stated ceiling.

Checks are marked hard (a promise the product makes, and a failure turns the case red) or soft (a preference it tries to honor, and a failure makes the case amber). Nothing is graded by a model. In particular, the model that produced the route is never asked whether the route is good.

What this does not establish. Whether a route is SAFE or PLEASANT to ride. No check in this harness establishes that. Traffic volume, shoulder width, pavement quality, sightlines and seasonal conditions are outside what OSM tags and this eval can see. Those claims would need field riding. Every route in this report passed software checks. None of them was ridden as part of this campaign.

Variability

The same sentence, five times

Everything after the parse is deterministic, so the only place run-to-run variation can enter is the one model call. To find out how much, 9 requests were parsed 5 times each with the cache disabled — a mix of crisply specified asks as a control and deliberately vague ones.

The reproducible number is the one about constraints — request type, distance, shape, climb cap, how many waypoints and avoid-places. Those are the fields that decide whether a candidate is accepted. 5 of 9 were identical on all of them across all five runs, and the split is not subtle: every crisply specified request was stable, and every unstable one was a request that genuinely underspecifies the ride or depends on session state.

Below that level, wording moves constantly and mostly harmlessly — the same start is written “Monona Terrace Madison WI” one run and “Monona Terrace, Madison, WI” the next, which geocodes identically. Only 2 of 9 drifted far enough to change the graded outcome. Free-text notes are excluded throughout: the model rewords those every run and they do not affect what gets generated.

So the honest reading of the headline number is this: a crisply specified request is reproducible, and a vague one is a distribution rather than an answer. “I want to go for a bike ride” produced four different distances across five runs, including one of zero miles that the server-side clamp caught. The product has no way to ask a clarifying question — it has to guess, and it does not tell the rider it guessed. That is a product gap this campaign measured rather than fixed, and it is the reason a single pass/fail count would overstate what is known here.

Engineering

A new ride request, answered as an edit to a route that did not exist

The campaign found four distinct defects. This one is worth walking through because the failure was total — the rider got no route at all for a request the product fully supports — and because the held-out set contained the same bug pointing the other way.

  1. The trigger

    Case D15 is an ordinary sentence: “I hate riding on Whitney Way — 22 mile loop from the Memorial Union Madison WI without it.” It asks for a new ride and gives a length, a start, and one road to stay off. The app came back with a refusal and no route at all.

  2. What actually happened

    The parse returned request_type: “edit_route”, mode avoid, place Whitney Way — and dropped distance_miles entirely, because the edit branch of the schema has no such field. The service then looked for a current route to edit, found none, and said so. Every layer below the parse behaved correctly. The request was classified wrong one step earlier, and the 22 miles the rider asked for never survived the first hop.

  3. Root cause

    The system prompt introduced the avoid edit mode with the example “I don't like riding Y” — almost exactly D15's opening clause. Nothing in the prompt said which signal decides between a new route and an edit, so a sentence carrying both a complaint and a complete route spec resolved toward whichever example it matched first.

  4. The same bug in the other direction, and worse

    The held-out set contained the mirror image. H23, “route me through Vilas Park and then the Arboretum”, states no length, so it is plainly an edit — but it parsed as a new route with an invented 10-mile distance, and the app replaced the rider's 18-mile route with a 10-mile one they never asked for. The next request in that session, a bare “undo” (H24), then had nothing to step back to. One misread sentence destroyed the work and the way back to it.

  5. The fix

    One rule at the top of the prompt, built on the only signal that actually separates the two cases: whether a length for the whole ride is stated. A stated length means a new route, even when the sentence also names roads to avoid or places to pass through. No stated length means an edit — with an explicit instruction never to invent a distance in order to treat it as a new route.

  6. Did it work? Half of it did

    This is where a report that only reported wins would stop. D15 is fixed and stable: parsed five more times with the cache disabled, it came back as a route with the avoid constraint intact every time, and the app now returns the 22-mile loop it always should have. H23 is not fixed. Parsed five times, it classified correctly three times and reverted to inventing a distance twice — so on the campaign run it failed, and H24 cascaded behind it. One prompt rule moved a reliable failure to a coin flip in that direction. That is an improvement and it is not a fix, and the page reports it as both.

FIRST decide "route" vs "edit_route", using the LENGTH OF THE WHOLE RIDE: - The request states a length or duration for the WHOLE ride ("30 miles", "a couple of hours", "45 mi loop") -> "route". It is still a "route" when it ALSO names roads to stay off or places to pass through; those belong in avoid_places / via_places. "I hate riding on X - give me a 22 mile loop from Y without it" is a ROUTE with avoid_places ["X"], NOT an avoid edit. - The request states no length for the whole ride and only describes a CHANGE ("go past X", "route me through X and then Y", "avoid Z", "make it longer", "end at W") -> "edit_route". NEVER invent distance_miles to turn such a request into a "route": replacing the rider's current route with a new one they did not ask for is the worst mistake you can make here.

Two things this does NOT claim. First, the rule was written against D15, a development-set case, so D15 passing is not independent evidence — the held-out cases are, and they say the rule generalizes only partly. Second, nothing here was tuned on H23 or H24: their expectations were frozen before the rule existed and neither was used to shape it, which is exactly why they can report a partial result instead of a flattering one. The repository also grew six parse-regression cases covering both directions of the boundary, so a future prompt edit cannot quietly undo the half that does work.

The remaining exposure is the interesting part. The parser cannot know whether a current route exists — that is session state the service holds, not something in the sentence. So the durable fix is not a better prompt at all: it is to make the mistake survivable, by recording a newly generated route's parent so undo can step back to the ride the rider had. That is designed and not built, deliberately: the only evidence for it in this campaign sits in the held-out set, and spending that evidence to chase one more green row would cost the one clean measurement this campaign has.

The other three

Correct internally, misleading on screen

Three of the four were the same shape, which is the part worth noticing. None of them was a wrong computation. In each case the program had already worked out the truth — that the router was down, that the lookup failed, that the stretch needs two laps — and then handed the user a sentence that did not contain it. A correct internal state and a misleading message is indistinguishable from a bug to the person using the thing, and no unit test asserting on return values would have caught any of them. They were found by writing down what the user should see and then checking the user-visible string against it.

A dead router told the rider to change their request
case D36 · routes/service.py · routes/pipeline.py · routes/providers.py

With the routing server unreachable, the progress log said ROUTING SERVER UNREACHABLE four times while the banner said “No route met the constraints — try a looser target or different distance.” The diagnosis existed; it never reached the person reading the screen, and it sent them to fix a request that was never the problem. The provider now records that the server never answered, and a one-second TCP preflight means a black-holed router costs a second rather than a dozen two-minute timeouts.

Scoring the scorer

Three checks that were wrong before they were right

An eval can be wrong in the same ways the thing it measures can. Three checks in this harness produced false failures on real routes and were corrected before any product change — recorded here because a report that only lists the subject's mistakes is not a report worth trusting. Each correction is pinned by a test asserting both that the legitimate geometry passes and that the broken geometry it exists to catch still fails; every case carries its scoring history in the saved results.

What went wrongWhy, and what replaced it
A 600 m gap threshold flagged three good routes.Wisconsin's section-line grid gives dead-straight half-mile and mile-long roads, which the router emits as a single segment. Raw gap length is not evidence of a break.
Requiring a sharp turn at one end still flagged grid corners.You turn 90° onto a section road and then run straight for half a mile: entered with a turn, left without one. The check now requires the long segment to be off-axis at both ends, which a corner never is and a splice always is.
The out-and-back detector scored an exact out-and-back at 0.6%.It resampled at a fixed step and compared by index, so the two halves drifted out of phase. Rewritten to compare positions by arc length. Until this was fixed the scorer was calling every out-and-back an accidental doubling-back.

Limitations

What is still unproven

  • No route in this campaign was ridden. Every claim here is about geometry and stated constraints. Whether a route is safe, pleasant, or has a shoulder is not something OSM tags and this harness can establish. The project's own history is field-testing — the devlog records 35 phases of riding routes and fixing what the ride exposed — but this report is not that evidence.
  • Elevation is not ground truth. SRTM-derived elevations carried in BRouter's GeoJSON output. The app's climb figure is routes/elevation.track_ascent, a model calibrated against RideWithGPS and one barometric .fit file; the devlog records that instruments themselves disagree by 8-16%, so +/-10% is the attainable accuracy. The eval reports the app's number AND an unsmoothed independent sum over the same elevations. Neither is ground truth -- only a barometric ride is.
  • One region. BRouter 1.7.10, self-hosted, profile fastbike-quiet, OSM extract tiles W90_N40 / W95_N40 (southern Wisconsin). Nothing here says the product works outside southern Wisconsin; other regions are a tile download, but that is a claim this campaign does not test.
  • Avoid-clearance is scored softly. A road at the start may be genuinely unavoidable, so meters-on-road is reported rather than gating the verdict. The number is the evidence; the judgement is the reader's.
  • Vague requests are not reproducible. Measured, not assumed: 5 of 9 repeated requests were identical on every constraint-driving field, and the ones that were not are the ones that underspecify the ride. The product cannot ask a clarifying question, so it guesses, and it does not say that it guessed.
  • One request type is still misread. An edit that states no length — “route me through Vilas Park and then the Arboretum” — is classified correctly three times in five. When it is not, the app generates a brand-new route and the rider's current one is gone, with nothing to undo back to. The durable fix is recording a new route's parent so undo can recover it; that is designed and not built, because the only evidence for it here is held out.
  • Single evaluator. The request set is written by the author. It is deliberately adversarial in places, but it is not a sample of real user traffic, and a real user base would produce phrasings this set does not contain.
  • The harness was wrong three times before it was right. Every correction is above and each is pinned by a test, but a first-run number from a new eval deserves less trust than this page's numbers now do, and that applies to anyone else's eval too.

Reproducibility

Rerunning this

The harness lives in the repository next to the app it tests. It drives routes.service.handle_request — the same entry point the web app and the CLI use — so a pass here is a pass for the shipped code path, not for a test double.

git clone https://github.com/NKimball1/route-gen-ai pip install -r requirements-dev.txt # offline: 100+ unit tests and the failure-injection cases, no keys, no server python -m pytest tests/ -q python -m evals.runner --run myrun --tier offline # live end-to-end: needs a self-hosted BRouter and an ANTHROPIC_API_KEY start_brouter.cmd python -m evals.runner --run myrun --tier live python -m evals.report --run myrun --compare baseline python -m evals.build_case_study --run myrun --baseline baseline

Parses are cached by request text, so re-running after a routing-side change costs nothing and scores the identical interpretation. Scoring is a pure function of the saved records, so python -m evals.rescore re-grades every run under the same rules when a tolerance changes.
